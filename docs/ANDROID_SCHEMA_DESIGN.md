# Android Collection Schema Design

This document describes the schema design for the `android_*` MongoDB collections produced by the data-processing pipeline, and the rules used to transform the raw payloads from android `.dbr` SQLite uploads into Mongo documents.

It applies to the collections defined in `study_framework_core/core/config.py:CollectionNames` (the `ANDROID_*` entries) and the processing functions in `study_framework_core/core/processing_scripts.py` (`_process_android_*_record`).

## Background

Each row from an android `.dbr` file is a 4-tuple `[event_id, timestamp, data_type, data_blob]`. The pipeline routes by `data_type` into one of the `android_*` collections.

Historically the processed documents were stored with a uniform wrapper:

```js
{
  uid: "...",
  event_id: <int>,
  timestamp: <float>,
  data_type: <int>,
  data: <whatever the sensor sent>,   // nested
  processed_at: <float>
}
```

This made cross-platform analytics awkward (iOS flattens, android nests) and required dot-notation queries like `db.android_location.find({"data.LATITUDE": ...})`.

This document defines the new flat schema for android collections.

## Design Principles

1. **Match iOS in shape, not in field names.** iOS collections are flat — promoted top-level fields like `latitude`, `longitude`, etc. Android collections will also be flat, but field names within each collection mirror the source data verbatim. iOS and android are intentionally separate collections; cross-platform code is expected to be device-aware.

2. **Preserve source data exactly.** Do not rename, lowercase, or fix typos in inner field names. If the android app sends `STAELLITES`, the document stores `STAELLITES`. Bugs in the source are filed against the android app, not papered over in processing.

3. **Lowercase only the *wrapper* key when promoting.** When a sensor payload is `{WIFIDATA: [...]}`, the flattened document gets a top-level key `wifidata`. The inner array contents (e.g., `SSID`, `BSSID`, `FREQUENCY`) are unchanged.

4. **Don't explode arrays into separate documents.** Sensors that return multiple items per scan (WiFi networks, Bluetooth devices, app-usage stats, call logs, SMS logs, running services) keep all items grouped under a single document. This preserves the "these were observed together" semantics.

5. **Drop uninformative scalar payloads.** When the entire payload is a constant value that conveys nothing the document doesn't already imply (collection name, timestamp), drop the field rather than store noise.

## Transformation Rules

| Source payload shape | Action |
|---|---|
| Dict, e.g. `{latitude: 42.3, longitude: -71.1, ...}` | Promote each key to top-level, preserving original case |
| Dict wrapping an array, e.g. `{WIFIDATA: [...]}` | Promote the wrapper to top level with lowercased key: `wifidata: [...]` |
| Raw array, e.g. `[{number, type, date, duration}, ...]` | Wrap under a semantic key (`calls`, `messages`) and store nested |
| Scalar with no information value, e.g. `1` or `"services_started"` | Drop entirely |
| Unknown / mixed shape | Keep nested under `data` (for `android_unknown_events` only) |

## Reserved Top-Level Fields

Every android document carries these fields regardless of sensor type. They are never derived from the payload:

| Field | Type | Source |
|---|---|---|
| `uid` | string | Participant UID |
| `event_id` | int | First column of the `.dbr` row |
| `timestamp` | float | Seconds since epoch (from `.dbr` row) |
| `data_type` | int | Sensor data_type (also implied by collection name; kept for explicitness) |
| `processed_at` | float | When the processing pipeline ingested the row |
| `_id` | ObjectId | Auto-generated by Mongo |

Unique index: `(uid, timestamp, event_id)` — defined in `init_collections`. Payload field names must not collide with the reserved names above; if any sensor ever sends a key called `uid` / `timestamp` / `event_id` in its payload, the existing reserved values take precedence (use `data.<key>` for the payload value as a side field if needed).

### `android_location` (data_type 2)

**Source** (`data` from row):

```js
{
  HASALTITUDE: true,
  ALTITUDE: -30.09018175077435,
  HASACCURACY: true,
  LONGITUDE: -71.0625908,
  ACCURACY: 100,
  LATITUDE: 42.3523231,
  PROVIDER: 'fused',
  STAELLITES: -1,
  SPEED: 0,
  NEWWORKLOCATIONSOURCE: '',
  BEARING: 0,
  HASBEARING: false,
  NEWWORKLOCATIONTYPE: '',
  HASSPEED: false,
  TRAVELSTATE: ''
}
```

**Target document:**

```js
{
  uid: "test_andrd",
  event_id: 6,
  timestamp: 1777074383.541,
  data_type: 2,
  processed_at: 1779842647.354079,
  HASALTITUDE: true,
  ALTITUDE: -30.09018175077435,
  HASACCURACY: true,
  LONGITUDE: -71.0625908,
  ACCURACY: 100,
  LATITUDE: 42.3523231,
  PROVIDER: 'fused',
  STAELLITES: -1,
  SPEED: 0,
  NEWWORKLOCATIONSOURCE: '',
  BEARING: 0,
  HASBEARING: false,
  NEWWORKLOCATIONTYPE: '',
  HASSPEED: false,
  TRAVELSTATE: ''
}
```

**Query example:** `db.android_location.find({LATITUDE: {$gt: 42}, ACCURACY: {$lt: 50}})`

### `android_location_ping` (data_type 902)

**Source:** scalar `1` (only ever observed value, confirmed via `distinct("data")`).

**Target document:** payload dropped. Document carries only reserved fields.

```js
{
  uid: "test_andrd",
  event_id: 5,
  timestamp: 1777074382.085,
  data_type: 902,
  processed_at: 1779842647.354061
}
```

**Rationale:** A ping with no associated data conveys only "the device pinged at time T," which is already captured by `(uid, timestamp)`. Storing a constant `1` adds no information.

**Query example:** `db.android_location_ping.find({uid: "test_andrd"}).count()` — count pings per user.

### `android_steps` (data_type 202)

**Source:**

```js
{
  start_time: Long('1777073901418'),    // milliseconds
  end_time: Long('1777074501992'),
  steps: 123,
  steps_since_boot: 12635,
  time_since_boot: 370987499
}
```

**Target document:**

```js
{
  uid: "test_andrd",
  event_id: 18,
  timestamp: 1777074501.993,
  data_type: 202,
  processed_at: 1779842647.354189,
  start_time: Long('1777073901418'),
  end_time: Long('1777074501992'),
  steps: 123,
  steps_since_boot: 12635,
  time_since_boot: 370987499
}
```

**Note:** `start_time`/`end_time` are milliseconds; the reserved `timestamp` field is seconds (it's the row-level event time from the .dbr file). When aggregating step counts over a window, use `start_time`/`end_time` for the actual reporting interval.

**Query example:** `db.android_steps.aggregate([{$match: {uid: "test_andrd"}}, {$group: {_id: null, total_steps: {$sum: "$steps"}}}])`

### `android_unknown_events`

This collection is a catch-all for `data_type` values not recognized by `_process_android_event_by_data_type`. By definition its payload shape is unknown.

**Special-case rule:** keep the original `data` field nested. Do not attempt to flatten — without knowing the shape, key collisions with reserved fields become possible.

**Target document:**

```js
{
  uid: "test_andrd",
  event_id: <int>,
  timestamp: <float>,
  data_type: <unrecognized int>,
  processed_at: <float>,
  data: <whatever the sensor sent — kept verbatim>
}
```

**Investigation workflow:** when this collection is non-empty, the team should:

1. Identify which `data_type`s are landing here: `db.android_unknown_events.distinct("data_type")`
2. Inspect samples: `db.android_unknown_events.aggregate([{$group: {_id: "$data_type", sample: {$first: "$data"}}}])`
3. Once the shape is understood, add a new `_process_android_<sensor>_record` function in `processing_scripts.py` and a new `ANDROID_<SENSOR>` collection in `config.py`.

## Migration Notes

Existing documents in these collections were stored with the old nested schema (`data: {...}`). After the processing code is updated, new documents will use the flat schema while existing documents remain in the old shape. Options:

- **Forward-only (recommended for dev):** delete existing android_* documents from the test database before deploying the change. Re-process `.dbr` files from `data_uploads/processed/phone/<uid>/` (move them back to `uploads/` and let the cron re-ingest).
- **Migration script (required for production):** if data needs to be preserved, write a one-shot script that updates each document in place: extract keys from `data`, promote to top-level, unset `data`. Not needed during the current android-testing phase since the data is throwaway.

## Open Questions

- **`android_activity` and `android_accelerometer`:** schemas to be added once sample data is available.
- **`data_type` overlap:** value `11` is reused — `android_services_started` (data_type 11) collides with iOS battery events (`event_id in [11, 111]`). This is fine because routing happens by collection, but worth noting.
- **Time-base mismatch:** `timestamp` is seconds; `start_time`/`end_time` (steps), `last_time_used` (app_usage), `date` (calllog/smslog) are milliseconds. Aggregations that mix these must normalize first.
